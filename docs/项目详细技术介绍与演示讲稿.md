# 智联物业 Agent：项目详细技术介绍与演示讲稿

这份材料写给没有亲自开发过本项目、但需要上台演讲和演示的学生。阅读目标不是背代码，而是能讲清楚：项目为什么做、系统怎么跑、用了哪些技术、技术之间怎么配合、创新点在哪里、真实落地还差什么。

---

## 一、项目背景：为什么要做这个系统

物业客服每天会接到很多住户电话，例如漏水、停电、噪音、电梯异常、燃气味、楼道烟味等。传统处理方式主要依靠人工：客服听电话、手动记录、判断问题类型、联系维修人员、再跟踪是否完成。

这种方式有几个明显问题：

1. **高风险发现慢**：烟味、燃气、电梯困人等事件如果判断慢，可能造成安全事故。
2. **记录不规范**：不同客服记录方式不同，容易漏掉楼栋、地点、联系人、现场情况等关键信息。
3. **派单不闭环**：电话接完后，问题是否派单、谁在处理、是否完成、是否回访，缺少统一追踪。
4. **管理不可量化**：主管很难快速知道哪些工单超时、哪些事件高风险、哪些问题最常发生。

所以本项目做了一个“物业来电智能助手”，帮助客服从接电话开始，到风险识别、生成工单、派单处理、回访归档，形成完整闭环。

---

## 二、项目一句话

> 本项目是一个面向物业来电场景的智能助手，可以在住户来电时识别风险，自动生成工单，并推动派单、处理、回访闭环。

更口语一点可以这样讲：

> 以前物业客服靠人工听电话、记问题、派维修。这个系统用 AI 帮客服把电话内容整理出来，判断风险高不高，并自动生成工单，最后跟踪到处理完成。

上台时要强调：

> 我们不是只做一个聊天机器人，而是把 AI 放进真实物业业务流程里，让系统从来电、识别、派单到回访都能管理起来。

## 三、系统整体流程

请先背熟这条流程线：

```text
住户来电
  ↓
语音或文本输入
  ↓
实时转写与风险预警
  ↓
规则引擎 + 多 Agent 分析
  ↓
生成风险等级、通话纪要、工单内容
  ↓
高风险进入人工确认
  ↓
后台工单池
  ↓
派单并自动进入处理中
  ↓
标记完成
  ↓
完成回访与归档
  ↓
数据看板、SLA 超时、规则配置、评测中心
```

给评委解释时可以这样说：

> 整个系统从物业来电开始。系统先接收语音或文本，把语音转成文字，然后同步做风险预警。接着由规则引擎和多 Agent 共同分析，生成风险等级、通话纪要和工单。高风险事件先进入人工确认，普通维修事件进入后台工单池。工单派单后自动进入处理中，最后完成处理和回访。这样就形成了从来电到闭环的完整流程。

## 四、项目技术架构

本项目可以分成四层理解：

```text
展示层：Streamlit 网页界面
  ↓
业务层：来电流程、工单池、SLA、规则配置、评测中心
  ↓
AI 层：faster-whisper 语音识别 + 规则引擎 + CrewAI 多 Agent
  ↓
数据层：SQLite / JSON 保存工单、规则、运行状态
```

### 1. 展示层：Streamlit

本项目的网页界面使用 **Streamlit** 开发。

Streamlit 是一个 Python Web 应用框架，适合快速做 AI 演示系统、数据看板、交互工具。它的优点是开发速度快，Python 代码就能直接生成网页。

在本项目里，Streamlit 负责展示：

- 客服工作台
- 来电演示按钮
- 录音/上传音频入口
- 实时转写文本框
- 分析结果页面
- 后台工单池
- SLA 超时监控
- 规则配置页
- 评测中心
- 数据看板

上台可以这样解释：

> Streamlit 负责把后端能力做成一个可以操作的网页界面。评委看到的按钮、表格、工单池和看板，都是 Streamlit 展示出来的。

### 2. 业务层：工单闭环逻辑

业务层不是 AI 模型，而是项目自己的流程控制逻辑。它负责把 AI 分析结果变成真实业务动作。

本项目的主要业务逻辑包括：

- 来电状态：未接入、来电中、通话中、录音完成。
- 工单生成：把分析结果写入后台工单池。
- 工单状态流转：待派单、处理中、已完成、已回访。
- 高风险确认：高风险事件先由人工确认，再进行应急联动。
- SLA 判断：根据风险等级计算是否超时。
- 外呼记录：记录模拟外呼或真实外呼请求。

上台可以这样解释：

> 业务层让系统不仅能“会分析”，而是能进入真实工作流程。它把来电分析结果转成工单，并跟踪派单、处理和回访。

### 3. AI 层：语音识别 + 规则引擎 + 多 Agent

AI 层是项目的智能核心，主要有三部分：

1. **faster-whisper 语音识别**：把语音转成文字。
2. **规则引擎**：用关键词和规则做安全兜底判断。
3. **CrewAI 多 Agent**：用多个 AI 角色协作完成总结、研判、工单生成。

这三部分不是互相替代，而是互相配合：

```text
语音识别负责“听懂电话”
规则引擎负责“稳定识别危险信号”
多 Agent 负责“理解内容并生成业务结果”
```

### 4. 数据层：SQLite 与 JSON

本项目使用本地数据文件保存运行状态，主要包括：

- 工单池数据
- 外呼记录
- 最近一次分析结果
- 风险规则配置

其中工单等运行状态使用本地 SQLite/JSON 保存，规则配置保存为 JSON 文件。

上台可以这样解释：

> 数据层负责把工单和规则保存下来。这样页面刷新后，工单池和配置不会马上丢失，系统更接近真实应用。

## 五、核心技术详细解释

## 1. 语音识别技术：faster-whisper / Whisper

### 1.1 什么是语音识别 ASR

ASR 是 Automatic Speech Recognition，意思是自动语音识别。它的作用是把人说的话变成文字。

在本项目中，住户打电话说的话需要先变成文字，系统才能继续判断风险、生成工单。

### 1.2 本项目用了什么技术

本项目使用的是 **faster-whisper**。

faster-whisper 是 Whisper 模型的一种高性能实现。Whisper 是 OpenAI 提出的语音识别模型，能够把多种语言的语音转成文字。faster-whisper 使用更高效的推理方式，让本地运行速度更快、资源占用更低。

本项目中的使用方式是：

- 用户可以通过浏览器录音。
- 用户也可以上传 WAV、MP3、M4A 等音频文件。
- 系统调用 faster-whisper，把音频识别成文字。
- 识别结果进入后续风险分析流程。

### 1.3 为什么需要语音识别

物业来电本质上是语音场景。如果没有 ASR，系统只能处理手动输入的文字。加入语音识别后，系统更接近真实电话业务。

上台可以这样讲：

> 语音识别是系统理解电话内容的第一步。我们使用 faster-whisper 把录音或上传音频转成文字，再把文字交给规则引擎和多 Agent 分析。

### 1.4 当前版本和真实电话的区别

当前比赛版本支持录音、上传音频和模拟流式文本。生产部署时，需要电话平台或 WebRTC 持续推送通话音频流。

可以诚实说明：

> 展示环境已经实现语音转文字和流式演示，电话平台接入可通过企业电话平台或 WebRTC 支持。接入后，后面的风险识别和工单闭环逻辑可以继续复用。

## 2. 多 Agent 技术：CrewAI 框架

### 2.1 什么是 Agent

Agent 可以理解为一个有角色、有任务、有目标的 AI 助手。

普通大模型通常是“问一句答一句”。Agent 更像一个岗位人员，它有自己的职责，例如负责总结、负责判断风险、负责生成工单。

### 2.2 本项目用了什么 Agent 框架

本项目使用的是 **CrewAI**。

CrewAI 是一个多 Agent 协作框架，可以把多个 AI 角色组织成一个团队，让它们按照任务流程协同工作。项目中的 `Present` 类就是 CrewAI 的核心组织方式。

在 CrewAI 中，一般有几个概念：

- **Agent**：角色，例如风险研判员、工单专员。
- **Task**：任务，例如判断风险、生成通话纪要。
- **Crew**：团队，把多个 Agent 和 Task 组织起来。
- **LLM**：底层大语言模型，本项目配置的是 DeepSeek 接口。
- **Tool**：工具，例如应急电话建议工具、外呼话术生成工具。

### 2.3 本项目中的 Agent 分工

项目中可以把 Agent 理解为以下几个岗位：

#### 风险研判 Agent

职责：判断来电是否属于紧急事件，输出风险等级、风险原因和建议动作。

示例：住户说“楼道有烟味”，风险研判 Agent 要判断可能是高风险事件。

#### 通话纪要 Agent

职责：把住户来电内容整理成清晰纪要，提取事件、地点、诉求、现场情况。

示例：把一段口语化电话整理成“某楼道疑似烟味，需要现场核查”。

#### 工单任务 Agent

职责：把来电内容变成物业可以执行的工单待办。

示例：生成“安排工程人员到现场排查，联系住户确认位置”。

#### 追问补全 Agent

职责：发现信息缺失并生成追问问题。

示例：如果住户没有说具体楼栋，系统会建议客服追问“请问具体是哪一栋哪一层？”

#### 闭环输出 Agent

职责：把前面各 Agent 的结果整合成最终输出。

示例：把风险、纪要、工单、追问汇总到结果页。

### 2.4 为什么用多 Agent

使用多 Agent 的原因是：物业来电处理不是单一问题，而是多个岗位协同。

如果只让一个 AI 一次性回答，结果可能混乱；多 Agent 可以把任务拆开，每个 Agent 负责一个明确环节。

上台可以这样讲：

> 我们使用 CrewAI 搭建多 Agent 协作流程，把 AI 拆成风险研判、通话纪要、工单生成、信息追问和闭环输出等角色。这样系统更像真实物业团队协作，而不是单纯聊天。

## 3. 规则引擎技术

### 3.1 什么是规则引擎

规则引擎就是提前设置一些判断规则，让系统遇到特定关键词或条件时，自动给出判断。

例如：

- 出现“烟味、冒烟、着火” → 高风险。
- 出现“燃气、煤气、泄漏” → 高风险。
- 出现“电梯困人、被困” → 高风险。
- 出现“漏水、堵塞、停电” → 中风险。
- 出现“噪音、咨询、投诉” → 低风险或普通工单。

### 3.2 为什么不能只用大模型

物业高风险事件涉及安全，不能完全依赖大模型。大模型有时可能理解不稳定，甚至出现误判。

规则引擎的价值是：

- 稳定：关键词命中就能触发。
- 可解释：能告诉评委命中了哪些词。
- 可配置：不同小区可以调整规则。
- 安全兜底：高风险词不会轻易漏掉。

### 3.3 本项目规则引擎的作用

本项目的规则引擎会输出：

- 命中的关键词
- 命中的规则名称
- 风险等级
- 是否应急
- 建议动作
- 规则分数

然后系统会把规则结果和 AI 结果合并，形成综合判断。

上台可以这样讲：

> 规则引擎负责安全兜底，大模型负责复杂语义理解。两者结合后，系统既有智能理解能力，也有稳定的安全判断能力。

## 4. 工单池与状态流转

### 4.1 工单池是什么

工单池是后台管理所有事件的地方。每个工单都有：

- 工单编号
- 来电内容
- 风险等级
- 工单类型
- 建议负责人
- 当前负责人
- 联系电话
- 工单状态
- 创建时间
- 处理日志

### 4.2 状态怎么流转

普通维修工单流程：

```text
待派单 → 处理中 → 已完成 → 已回访
```

高风险应急工单流程：

```text
待人工确认 → 应急联动确认 → 处理中 → 已完成 → 已回访
```

本项目已经做了一个产品细节：派单后不会停留在“已派单”，而是自动进入“处理中”。这样更符合真实业务，因为维修人员接到工单后，任务就已经进入处理阶段。

上台可以这样讲：

> 工单池体现的是业务闭环。系统不是分析完就结束，而是继续追踪这个问题有没有派单、有没有处理、有没有回访。

## 5. SLA 超时机制

### 5.1 什么是 SLA

SLA 是 Service Level Agreement，意思是服务时限要求。

在物业场景中，不同事件要有不同处理时限。例如：

- 高风险事件要马上确认。
- 中风险维修要尽快派单。
- 低风险咨询可以按普通流程处理。

### 5.2 本项目如何设置 SLA

当前项目设置：

- 高风险/应急事件：1 分钟内确认。
- 中风险事件：10 分钟内响应。
- 低风险事件：24 小时内处理或回访。

系统会根据工单创建时间和风险等级计算是否超时，并在 SLA 页面展示。

上台可以这样讲：

> SLA 让系统具备管理能力。它不仅能识别事件，还能提醒哪些工单已经超时，帮助物业主管及时盯办。

## 6. 规则配置页

规则配置页是给物业管理人员用的。它可以修改：

- 规则名称
- 关键词
- 风险等级
- 是否紧急
- 规则分数
- 建议动作
- 是否启用

为什么这很重要？

因为不同小区问题不一样。有的小区电梯问题多，有的小区漏水问题多，有的小区投诉噪音多。如果所有规则都写死在代码里，就不方便落地。

上台可以这样讲：

> 规则配置页让系统可以适配不同小区。物业人员不用改代码，也能调整关键词和风险等级。

---

## 7. 评测中心

评测中心用于检查系统判断是否可靠。

它用固定测试样本测试：

- 规则准确率
- 高风险召回率
- 期望风险和实际风险是否一致

其中“高风险召回率”很重要，意思是：真正高风险的样本，有多少被系统识别出来。

上台可以这样讲：

> 评测中心用于证明系统不是拍脑袋判断，而是可以用测试样本验证效果。后续真实落地后，可以把历史来电数据整理成更大的测试集。

### 8.1 页面外呼演示

## 九、项目文件与技术对应关系

学生不需要背全部代码，但可以知道大概位置：

- `app.py`：主界面和主要业务流程，包含客服工作台、工单池、SLA、评测中心等页面。

- `output/`：生成的 PPT 或报告文件。

上台可以这样讲：

> 项目主流程集中在 app.py，AI Agent 配置在 crew.py，规则引擎单独封装在 risk_engine.py，这样界面、AI 和规则是分层管理的。

## 十、项目创新点

### 创新点一：边通话边识别风险

传统客服通常是通话结束后再整理记录。本项目可以在通话过程中同步识别风险信号，例如烟味、燃气、电梯困人。

### 创新点二：规则引擎 + CrewAI 多 Agent

规则引擎保证高风险识别稳定，多 Agent 负责复杂语义理解和业务输出。两者结合比单纯大模型更可靠。

### 创新点三：从识别到闭环

很多项目只做到“识别风险”，本项目继续完成工单生成、人工确认、派单处理、完成回访。

### 创新点四：可配置、可评测、可管理

规则配置页、评测中心和 SLA 超时机制，让系统更接近真实工业应用，而不是只做演示页面。

## 十一、项目演示步骤

### 步骤 1：打开客服工作台

说明这是物业客服接电话的工作界面。

### 步骤 2：演示高风险来电

选择“疑似火灾”或“燃气泄漏”。

### 步骤 3：展示实时识别

点击“接收下一段语音”或“自动流式播放”，展示文本逐步出现和风险预警。

### 步骤 4：送入多 Agent 分析

## 十二、三分钟演讲稿

各位评委老师好，我们的项目叫“智联物业 Agent：物业来电智能助手”。

这个项目面向物业客服来电场景。传统物业客服在接到住户电话后，需要人工记录、人工判断风险、人工派单，遇到烟味、燃气泄漏、电梯困人等高风险事件时，容易出现发现慢、记录乱、处理不闭环的问题。

我们的系统可以在住户来电时，把语音或文本转成可分析内容，并同步进行风险识别。如果系统发现烟味、燃气、电梯困人等关键词，会立即提示高风险。随后，多 Agent 会生成通话纪要、风险判断、工单内容和建议追问。

技术上，我们使用 Streamlit 搭建交互界面，使用 faster-whisper 进行语音识别，使用规则引擎进行安全兜底，同时使用 CrewAI 搭建多 Agent 协作流程。多 Agent 包括风险研判、通话纪要、工单生成、追问补全和闭环输出等角色。后台有工单池，可以完成派单、处理中、完成和回访。系统还加入了 SLA 超时机制、规则配置页和评测中心。

本项目的创新点主要有四个。第一，支持边通话边识别风险；第二，采用规则引擎和 CrewAI 多 Agent 双重判断；第三，不仅能识别风险，而是形成从来电到回访的完整闭环；第四，具备可配置、可评测、可管理的能力，更接近真实物业系统。

目前这个版本已完成来电演示、录音识别、风险分析和工单闭环展示。生产落地时，可接入物业电话平台或 WebRTC，把通话音频流传给系统。接入以后，现有的风险识别、工单生成和闭环处置逻辑可以继续复用。

## 十三、评委常见问题回答

### Q1：你们用了什么 Agent 框架？

答：

> 我们使用 CrewAI 框架来组织多 Agent。CrewAI 可以定义不同角色的 Agent 和任务流程，本项目中包括风险研判、通话纪要、工单生成、追问补全和闭环输出等角色。

### Q2：语音识别用的什么技术？

答：

> 语音识别使用 faster-whisper，它是 Whisper 模型的高性能实现。它可以把录音或上传音频转成文字，然后交给规则引擎和多 Agent 分析。

### Q3：为什么不用纯大模型？

答：

> 因为物业高风险场景关系安全，不能完全依赖大模型。我们加入规则引擎做安全兜底，确保烟味、燃气、电梯困人等关键词能稳定识别。大模型负责复杂语义理解，规则负责稳定和可解释。

### Q4：现在是电话平台接入吗？

答：

> 当前展示版已支持来电接入、录音识别和流式识别流程；生产部署时可接入电话平台、呼叫中心或 WebRTC，把通话音频流推送给系统。

### Q5：这个项目有什么实际价值？

答：

> 它可以减少客服记录时间，提高高风险事件响应速度，并让每个事件都有工单、有状态、有负责人、有回访记录。

### Q6：系统误判怎么办？

答：

> 高风险事件不会由 AI 直接自动处置，而是先进入人工确认。人工确认后再进行应急联动，这样可以降低误判风险。

### Q7：怎么适配不同小区？

答：

> 系统有规则配置页，不同小区可以根据常见问题调整关键词、风险等级、是否紧急和建议动作。

### Q8：怎么证明系统有效？

答：

> 系统有评测中心，可以用测试样本验证规则准确率和高风险召回率。后续可以导入真实历史来电形成更大的测试集。

### Q9：SLA 有什么作用？

答：

> SLA 是服务时限管理。高风险事件如果超时未处理，系统会提示，方便主管及时盯办。

### Q10：真实落地还需要什么？

答：

> 生产落地可接入物业电话平台或 WebRTC，接入企业工单系统，并完成短信或语音外呼平台的企业认证和模板审核。
